# 14. Live Mode Safety Foundation (`hostkit/safety`)

This document specifies **Stage 1 of Live Mode**: the shared, provider-neutral safety, recovery-journal, cost-metering, and supervision package (`github.com/lmctl-ai/lmcloud/hostkit/safety`). It makes **zero real cloud calls** itself and is strictly additive to `hostkit`.

---

## 1. Operator Decisions & Stage 1 Scope

1. **Default remains sim/fake:** No host ever contacts a live cloud endpoint unless the double opt-in gate (`LMCLOUD_LIVE=1` **and** `LM<HOST>_LIVE=1`) and a validated `live-policy.json` file are supplied.
2. **Stage 1 live provider scope:** AWS only for now (account `254332045686`, region `us-east-1`, IAM role `awsspot-admin`). Other providers (`azure`, `gcp`, `oci`) remain disabled in `ResolveExecutionMode` until explicitly enabled in later stages.
3. **Mutation boundaries:** Live runs are either **read-only** (`allow_mutations: false`) or permitted to create **new** resources only when they carry the run's reserved prefix (`lmcloud-conf-<run12>-`) and mandatory ownership metadata (`lmcloud_run_id`, `lmcloud_owner_nonce`, `lmcloud_create_token`, `lmcloud_created_at`).
4. **Never adopt or delete unowned resources:** Pre-existing resources (even if they share the `lmcloud-conf-<run12>-` prefix) that lack this run's journaled `owner_nonce` and `run_id` are treated as foreign collisions (`CONFLICT` / `ForeignResourceCollision`) and are **never** adopted or deleted.
5. **No `--force-stale` and no Windows live mode:** Journal concurrency is governed strictly by POSIX `flock(LOCK_EX|LOCK_NB)` on `0600` files inside `0700` directories. Windows explicitly refuses live mode (`WindowsLiveUnsupported`).

## 3. Core Safety Invariants

1. **Intent-Before-Create, Pre-Create Absence Proof & Sticky Retention:**
   - `Journal.BeginCreate` / `BeginCreateWithBytes` generates a 128-bit `OwnerNonce` (resource identity) and a 128-bit `CreateToken` (attempt idempotency token), writes the `intent` JSONL record (including `ReservedNanoUSD` and `PayloadBytes`), and `fsync`s the journal file **before** any provider call.
   - Before dispatching `CreateBucket` or `CreateQueue`, `LiveGuard` runs a metered `ReadOwnership` probe to prove prior absence (or convergence of an earlier pending attempt in the same run), preventing duplicate-create tagging adapters from ever overwriting a foreign or untagged resource's tags.
   - Retries of a `pending` create reuse the persisted `OwnerNonce` and `CreateToken` and durably update `IntentAtUnix` on disk to the latest attempt timestamp.
   - Every child object or queue operation freshly re-verifies remote ownership of the parent bucket/queue via a metered `ReadOwnership` check and quarantines the parent as `retained` on mismatch.
   - Any pre-create, post-create, or parent ownership mismatch or ambiguous state records the resource as `retained` (`Retain: true`, `StateRetained`). Retained entries are sticky across `Confirm`, `Compact`, and disk reopen, are short-circuited in `CreateBucket`/`CreateQueue` before touching the adapter, and are refused by all guard `Delete*` operations.
2. **Dedicated `.lock` Lease, Journal Health Gate & Durable Pre-Dispatch Reservations:**
   - `OpenJournal` holds its `flock(LOCK_EX|LOCK_NB)` lease on a dedicated `<run_id>.lock` sibling file that is never renamed or unlinked during `Compact()`, eliminating any lease race across atomic `.jsonl.tmp -> .jsonl` renames.
   - If any write, short write, or `fsync` fails on an open `Journal`, `appendLocked` immediately truncates and seeks the file back to the last good offset and poisons the `Journal` instance.
   - Every guarded operation checks `Journal.CheckHealth()` and durably persists an attempt-level reservation (`EventReserve` or `EventIntent` with `AttemptID`, worst-case `ReservedNanoUSD`, message count, and `PayloadBytes`) to the journal **before** dispatching to the provider, and settles that reservation strictly by `AttemptID` (`EventSettle` or `EventConfirmed`) after dispatch. Ownership/read probes never clear an outstanding create reservation, overwrites on confirmed objects accumulate `TotalPayloadBytes` and reserve their attempt cost before dispatch, and `GetObject` reserves max bounded egress cost before dispatch and settles actual downloaded egress after return.
   - `Compact()` and `OpenSession` persist and restore each active entry's `ReservedNanoUSD` as well as any unresolved `PendingAttempts` on disk so pending reservations survive readback, sweep, compaction, and reopen without loss or double-counting.
3. **Create-Token & Sanitized Endpoint Redaction:**
   - Every `OwnerNonce` and `CreateToken` is registered with `hostkit.ErrorState.AddRedaction` before network dispatch so echoed tokens in provider error messages or codes are replaced with `[create-token]`.
   - `RedactEndpoint` strips any URL userinfo, query parameters, or fragments before persisting `JournalMeta.Endpoint`, and `RedactEndpoint`, `ValidateLiveOrigin`, and `ReplayJournal` return sanitized parser errors without echoing raw secret-bearing URLs.
4. **LIFO Ownership-Revalidating Sweep, Metered Recovery & Grace Reporting:**
   - Active sweeps (`Apply: true` and `SweepAllStale`) fail closed if a regional price table or `CostMeter` cannot be loaded, always restore cumulative campaign spend and pending reservations from the run journal (`RestoreMeterFromState`) so standalone `--sweep --apply` invocations never reset the campaign's cost cap, and journal every physical recovery attempt (`EventReserve` -> `EventSettle`) before and after dispatch (`AttestIdentity`, `ReadOwnership`, bucket child `object_list`, `DeleteOwned`, `PollDelete`, and `FindOwned`).
   - Child objects (`object`) are swept in reverse creation order (LIFO) before top-level buckets (`bucket`) and queues (`queue`). Queue messages are tracked for cost (`EventCost`), cumulative count (`MessagesSent`), and payload bytes (`TotalPayloadBytes`), and are removed when their owning queue (`queue`) is deleted during the sweep.
   - Before deleting a bucket (in either `GuardStore.DeleteBucket` or `Sweep`), `RemoteOwnership.ChildrenVerified` must be `true`; if child listing could not be verified or if any unjournaled/unowned child object is present in `RemoteOwnership.ChildKeys`, the bucket is retained and never deleted.
   - `Sweep` honors a grace period (`DefaultPendingIntentGraceSeconds = 10s`, matching `DefaultMaxRequestTimeoutSeconds = 10s`) measured from the latest `IntentAtUnix` before tombstoning a `pending` entry that reads as absent, reporting in-grace entries in `SweepReport.Pending` with `SweepReport.Clean() == false` so callers know unresolved work remains.
   - Asynchronous deletions are polled via `RecoveryAdapter.PollDelete` until convergence before writing the `deleted` record.

## 4. Stage 2 AWS S3 Conditional Bindings & `us-east-1` `CreateBucket` Residual Risk

1. **Atomic Conditional S3 Object Writes & Deletes (`If-None-Match` / `If-Match`):**
   - In live mutation mode (`LMAWS_LIVE_MUTATE=1`), `PutObject` verifies pre-put absence or confirmed journal ownership and binds the physical S3 `PUT` with `If-None-Match: *` when creating a new key and `If-Match: "<journaled-etag>"` when overwriting a confirmed object owned by the current run.
   - `DeleteObject` binds the physical S3 `DELETE` with `If-Match: "<journaled-etag>"`.
   - Any HTTP `412 Precondition Failed` or `409 Conflict` response is treated as a foreign resource collision (`CONFLICT` / `ForeignResourceCollision`), marks the object `StateRetained` in the run journal, and is never retried as an unconditional write.
2. **Owned-Read Binding on `GetObject` / `HeadObject`:**
   - In live mutation mode, `GetObject`, `HeadObject`, and `ListObjects` require the parent bucket (and, for `GetObject`/`HeadObject`, any existing object) to be `StateConfirmed` in the run journal and verified via remote ownership tags (`VerifyMatchesEntry`, including `ETag` matching).
   - `GetObject` and `HeadObject` pass `If-Match: "<proven-etag>"` (and `VersionId` when present) on the physical S3 read, verify that the response `ETag` matches the proven journal `ETag`, and re-verify `GetObjectTagging` before returning payload bytes so a concurrent replacement between the ownership probe and `GET` is refused (`PermissionDenied` / `UnownedResourceReadRefused`) and retained.
3. **S3 `us-east-1` `CreateBucket` Semantics & Accepted Residual Risk:**
   - **AWS S3 protocol limitation:** Unlike S3 `PutObject` (which supports `If-None-Match: *` and atomic `x-amz-tagging` on `PUT`) and SQS `CreateQueue` (which accepts creation-time `Tags` atomically and rejects tag mismatches with `QueueAlreadyExists`), AWS S3 `CreateBucket` does not accept tags in the `CreateBucket` request, does not support `If-None-Match: *`, and in `us-east-1` (when `LocationConstraint` is omitted) returns `200 OK` (and resets default bucket ACLs) if a bucket with the same name already exists in the same AWS account (`BucketAlreadyOwnedByYou` behavior).
   - **Defense-in-depth controls:**
     1. **Dedicated single-tenant account & IAM scope:** Live conformance runs exclusively in dedicated AWS account `254332045686` (`us-east-1`) under role `arn:aws:iam::254332045686:role/lmcloud-conformance-ci`, whose IAM policy permits S3/SQS actions only on `lmcloud-conf-*` resources, with GitHub Actions `concurrency` serialization (`cancel-in-progress: false`).
     2. **>= 48 bits of per-run cryptographic randomness in resource names:** Every `RunID` embeds 48 bits (`<12hex>`) of `crypto/rand` entropy (`lmcloud-conf-<12hex>-`), and conformance runners append an additional 32-bit random suffix (`lmcloud-conf-<12hex>-<8hex>-<slug>`), providing 80 bits of unguessable per-run randomness so another actor cannot predict a bucket name before `CreateBucket`.
     3. **Pre-create absence proof:** Before dispatching `CreateBucket`, `GuardStore.CreateBucket` runs a metered `ReadOwnership` check (`HeadBucket` + `403 GetBucketLocation` probe) and refuses with `ForeignResourceCollision` (`StateRetained`) if the bucket already exists (tagged or untagged).
     4. **Post-`CreateBucket` / pre-`PutBucketTagging` empty & tagless check:** Immediately after `CreateBucket` returns `200 OK` and before calling `PutBucketTagging`, `liveRawBackend.CreateBucket` executes metered `GetBucketTagging` and `ListObjectsV2(MaxKeys: 1)` calls. If any foreign/mismatched tags or any objects exist, `PutBucketTagging` is skipped and the bucket is quarantined as `StateRetained`.
     5. **Post-tag token & creation-timestamp verification (`VerifyMatchesEntry`):** After `PutBucketTagging`, `ReadOwnership` verifies that remote tags carry this run's exact `RunID`, 128-bit `OwnerNonce`, and 128-bit `CreateToken`, and that both `lmcloud_created_at` and any reported S3 `CreationDate` (`ServerCreatedAtUnix`) are `>= IntentAtUnix`. Any bucket whose tag token mismatches or whose `CreationDate < IntentAtUnix` is marked `StateRetained` and is **never** deleted by `DeleteBucket` or `Sweep`.
   - **Accepted residual risk:** Two narrow protocol-level windows remain inherent to S3 `us-east-1`: (a) if the runner is killed after `CreateBucket` succeeds and before `PutBucketTagging` completes, the resulting untagged bucket is retained (`StateRetained`, exit code `1` on sweep) for manual cleanup rather than deleted without tag proof; and (b) if another actor in the same AWS account simultaneously guesses the 80-bit random `lmcloud-conf-<12hex>-<8hex>-*` name and creates an empty, untagged bucket in `us-east-1` within the sub-second window between `HeadBucket (404)` and `CreateBucket (200)` with `CreationDate >= IntentAtUnix`, S3 `us-east-1` returns `200 OK` indistinguishable from fresh creation. Under the single-tenant account, serialized workflow concurrency, and `>= 48`-bit random naming invariants above, this residual risk is accepted.
