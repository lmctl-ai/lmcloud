# 03 — Object Storage Conformance Scenarios (`lmcloud`)

Each conformance scenario below is implemented as a standalone `lmscript` program under `tests/conformance/object-storage/NN-<scenario>.lms` and executed via `tests/run-conformance.sh <host-binary> [endpoint]`.
Simulators are driven exclusively by `lmscript` through the `lm<provider>` host (`run_lmcode(program, {command:[ARGV[0], "--lmcode", "$DSLFILE"]})`), never via `curl` or direct HTTP clients.

> **Execution status:** All 12 `.lms` conformance programs pass static type and bytecode compilation checks (`lmscript --check`) against `schema/lmcloud.dsl.json`. They cannot be executed at runtime yet because the four Go hosts (`lmaws`, `lmazure`, `lmgcp`, `lmoci` on `lmctl-ai/lmcode-go`) have not been implemented yet.

## Scenarios

1. **`01-bucket-lifecycle`** (`tests/conformance/object-storage/01-bucket-lifecycle.lms`) — Creating a new bucket returns `true`, makes `bucket_exists` return `true` and includes the bucket in `bucket_list` in sorted order, and deleting the empty bucket returns `true` and makes `bucket_exists` return `false`.
2. **`02-bucket-idempotency-and-nonempty-guard`** (`tests/conformance/object-storage/02-bucket-idempotency-and-nonempty-guard.lms`) — Calling `bucket_create` on an existing caller-owned bucket returns `false` without error, calling `bucket_delete` on a bucket containing an object fails with `ErrorCode.CONFLICT` (`BucketNotEmpty`) on all four providers (including Azure), and calling `bucket_delete` on an already-deleted bucket returns `false` without error.
3. **`03-object-crud-text-and-unicode`** (`tests/conformance/object-storage/03-object-crud-text-and-unicode.lms`) — Putting a UTF-8 object with quotes, newlines, and multi-byte Unicode (`雪 / 🚀`) round-trips byte-for-byte via `object_get`, reports accurate byte length via `object_head`, and after `object_delete` leaves `object_head(...).exists() == false` and `object_get` failing with `ErrorCode.NOT_FOUND`.
4. **`04-object-binary-and-empty-roundtrip`** (`tests/conformance/object-storage/04-object-binary-and-empty-roundtrip.lms`) — Putting both a zero-byte payload (`""`) and a raw binary payload containing NUL (`\x00`) and non-UTF-8 bytes (`\xff\xfe`) preserves exact byte length (`size()`) and exact `str_hex_encode(object_get(...))` across all four providers.
5. **`05-object-overwrite-and-etag`** (`tests/conformance/object-storage/05-object-overwrite-and-etag.lms`) — Overwriting an existing key via `object_put` atomically replaces the body and `size()`, returns a non-empty normalized `etag()` (without surrounding quotes), and updates the ETag when the payload changes.
6. **`06-object-metadata-and-content-type`** (`tests/conformance/object-storage/06-object-metadata-and-content-type.lms`) — Uploading an object with explicit `content_type` (`"application/json"`) and custom `StrMap` metadata (`str_map().set("env", "staging").set("build_id", "42")`) returns matching `content_type()` and normalized lowercase metadata entries via `object_head` with provider header prefixes (`x-amz-meta-`, `x-ms-meta-`, `opc-meta-`) stripped.
7. **`07-object-list-prefix-and-order`** (`tests/conformance/object-storage/07-object-list-prefix-and-order.lms`) — Seeding hierarchical keys (`logs/2026/a.txt`, `logs/2026/b.txt`, `logs/2025/c.txt`, `root.txt`) and calling `object_list` with prefix `"logs/2026/"` and `""` returns only matching keys in deterministic ascending UTF-8 byte order with accurate `size()` and `etag()` on each `ObjectSummary`.
8. **`08-object-list-pagination`** (`tests/conformance/object-storage/08-object-list-pagination.lms`) — Seeding 5 objects under a common prefix and paging with `object_list(bucket, prefix, 2, token)` until `!page.has_more()` visits all 5 keys in lexicographical order across 3 pages (`2 + 2 + 1`) with zero duplicates or gaps.
9. **`09-delete-missing-idempotency`** (`tests/conformance/object-storage/09-delete-missing-idempotency.lms`) — Calling `object_delete` on a non-existent key inside an existing bucket (and calling `object_delete` a second time after deleting a real object) succeeds idempotently with `ErrorCode.OK` on all four providers without raising `NOT_FOUND`.
10. **`10-not-found-errors`** (`tests/conformance/object-storage/10-not-found-errors.lms`) — Calling `object_get`, `object_head`, `object_delete`, or `object_list` on a non-existent bucket fails with `ErrorCode.NOT_FOUND`, whereas `bucket_exists` on a missing bucket and `object_head` on a missing key in an existing bucket return `false` / `exists() == false` with `ErrorCode.OK`.
11. **`11-validation-guards`** (`tests/conformance/object-storage/11-validation-guards.lms`) — Passing non-portable bucket names (`"Bad_Bucket"`, `"a--b"`, `"ab"`), invalid object keys (`"/leading"`, `"a//b"`, `"../escape"`), or invalid metadata keys (`"bad-hyphen"`, `"1digit"`) fails pre-flight with `ErrorCode.INVALID_ARGUMENT` (`http_status() == 0`) before any network call.
12. **`12-auth-enforced-denial`** (`tests/conformance/object-storage/12-auth-enforced-denial.lms`) — Against `<provider>sim --auth enforce`, requests with missing/bad credentials fail with `ErrorCode.UNAUTHENTICATED` and IAM/RBAC-denied actions fail with `ErrorCode.PERMISSION_DENIED`, never masquerading as `bucket_exists == false` or `ObjectMeta.exists() == false`.

## Sim enhancements

Inspection of `/home/ubuntu/cloud/{awssim,azuresim,gcpsim,ocisim}` source overlays, docs, and test suites identified the following concrete simulator gaps/quirks relevant to the 12 conformance scenarios:

1. **`awssim` — `src/main/java/ai/lmctl/awssim/AuthFilter.java` (lines 37–38, 115–118, 130–134) & `scripts/test-auth.py`:**
   - **What is missing/wrong:**
     - `SUPPORTED.get("s3")` (lines 37–38) lists `"ListAllMyBuckets"`, `"CreateBucket"`, `"DeleteBucket"`, `"ListBucket"`, `"GetBucketLocation"`, `"PutBucketTagging"`, `"GetBucketTagging"`, `"DeleteBucketTagging"`, `"PutObject"`, `"GetObject"`, `"DeleteObject"`, omitting `"HeadBucket"` and `"HeadObject"` if upstream `IamActionRegistry.resolveRoute("s3", ctx)` resolves `HEAD /{bucket}` or `HEAD /{bucket}/{key}` to distinct action names (and `scripts/test-auth.py` only tests `PUT` in `--auth enforce` mode, never `HEAD`).
     - In `AuthFilter.reject()` (lines 130–134), S3 `HEAD` rejections (`HEAD /{bucket}` for `bucket_exists` and `HEAD /{bucket}/{key}` for `object_head`) return HTTP `403` for both `SignatureDoesNotMatch` / `InvalidAccessKeyId` (`UNAUTHENTICATED`) and `AccessDenied` (`PERMISSION_DENIED`), while HTTP `HEAD` responses strip the XML entity body on the wire. Preserving `x-amzn-errortype` (already set on line 133) and verifying `HEAD` route resolution in `scripts/test-auth.py` ensures `bucket_exists` and `object_head` reliably distinguish `UNAUTHENTICATED` vs `PERMISSION_DENIED` in scenario `12`.
2. **`azuresim` — `src/main/java/ai/lmctl/azuresim/StorageAuth.java` (lines 152–160, 219–220) & `scripts/test-storage.py`:**
   - **What is missing/wrong:**
     - `scripts/test-storage.py` verifies basic container/blob CRUD and `prefix` filtering (lines 29–39), but never tests `maxresults` + `marker` -> `<NextMarker>` pagination (`08-object-list-pagination`) or `x-ms-meta-*` custom metadata headers on `HEAD` in open mode.
     - Upstream `floci-az` `DELETE /{account}/{container}?restype=container` deletes non-empty containers without returning `409 Conflict` (handled by `lmazure`'s pre-flight `maxresults=1` check per Decision 3, or optionally enforced in `azuresim`).
     - `StorageAuth.error()` (lines 152–160) returns HTTP `403` for both `AuthenticationFailed` and `AuthorizationPermissionMismatch` (differentiated via the `x-ms-error-code` response header on line 155, which `lmazure` must inspect on both `HEAD` and body responses for scenario `12`).
3. **`gcpsim` — `src/main/java/ai/lmctl/gcpsim/PermissionFilter.java` (lines 73–98) & `scripts/test-lifecycle.py` (lines 53–68):**
   - **What is missing/wrong:**
     - In `scripts/test-lifecycle.py` (lines 53–59), setting custom `metadata` and `contentType` on an object requires two separate HTTP calls (`POST /upload/storage/v1/b/{b}/o?uploadType=media` followed by `PATCH /storage/v1/b/{b}/o/{k}`), because single-request `uploadType=multipart` with binary payloads + JSON `metadata`/`contentType` is only tested for auth rejection in `scripts/test-auth.py` (lines 109–112), not for end-to-end binary + metadata storage in `floci-gcp`. Furthermore, in `--auth enforce` mode, a 2-step `POST` + `PATCH` requires both `storage.objects.create` (line 94) and `storage.objects.update` (line 97). `gcpsim` should verify/support single-request `uploadType=multipart` preserving raw binary bytes alongside JSON `metadata` and `contentType` (or `lmgcp` must use `uploadType=multipart`).
     - `scripts/test-lifecycle.py` (line 64) only tests unpaginated `prefix=dir/` listing and never verifies `maxResults` + `pageToken` -> `nextPageToken` pagination (`08-object-list-pagination`) or `409` on deleting a non-empty bucket (`02-bucket-idempotency-and-nonempty-guard`).
4. **`ocisim` — `src/main/java/ai/lmctl/ocisim/OciAuthFilter.java` (lines 205–219) & `scripts/test-integration.py` (lines 207–276):**
   - **What is missing/wrong:**
     - `OciAuthFilter.reject()` (lines 213–219) writes `"code": "NotAuthenticated"` (`401`) or `"code": "NotAuthorizedOrNotFound"` (`403`) only into the JSON response body without setting an HTTP response header; on `HEAD /n/{ns}/b/{b}` (`bucket_exists`) and `HEAD /n/{ns}/b/{b}/o/{o}` (`object_head`), the HTTP response has no body, so `OciAuthFilter.reject()` should also emit `opc-error-code` header (or `lmoci` must map status `401` -> `UNAUTHENTICATED` and `403` -> `PERMISSION_DENIED` when the body is empty).
     - `scripts/test-integration.py` (lines 234–245) tests basic `PutObject`/`HeadObject`/`GetObject`/`ListObjects`/`DeleteObject`, but never tests `opc-meta-*` custom metadata preservation on `PutObject`/`HeadObject` (`06-object-metadata-and-content-type`) or `limit` + `start` -> `nextStartWith` pagination on `ListObjects` (`08-object-list-pagination`).
